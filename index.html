데이터 모델링의 이해

현실의 업무를 데이터베이스로 옮기는 첫 단계입니다. 이 파트의 핵심은 용어 구분 — 데이터 모델·엔터티·속성·관계·식별자의 뜻을 분명히 잡는 것입니다.

1. 데이터 모델의 이해

데이터 모델이란 현실 세계의 복잡한 정보를 컴퓨터에 저장하기 위해 그린 설계 도면입니다. 현실 업무를 데이터베이스로 표현하기 위해 추상화하는 작업이죠.

💡 쉽게 말하면

데이터 모델링은 현실을 지도로 그리는 일이에요. 실제 도시엔 건물·사람·차가 가득하지만 지도엔 길과 주요 건물만 간단히 그리죠. 똑같이, 복잡한 회사 업무에서 "저장·관리할 정보"만 골라 깔끔한 그림으로 옮기는 게 데이터 모델링입니다. (예: 회원-상품-주문 정보를 어떻게 저장하고 연결할지 설계)

데이터 모델링의 3가지 특징 — '추·단·명'

특징 1

추상화

공통 특징을 찾아 간략하게. 핵심만 남깁니다.

특징 2

단순화

복잡함을 피하고 누구나 이해하게 표현합니다.

특징 3

명확화

해석이 모호하지 않게, 한 가지 의미만 갖도록.

데이터 모델링 3단계 — 개념 → 논리 → 물리 ('개-논-물')

1단계 · 개념적

개념적 모델링

전사적(업무 전체) 관점. 추상화 수준이 가장 높음. 핵심 엔터티·관계를 뽑아 개념 ERD 작성.

2단계 · 논리적

논리적 모델링

속성·PK·FK를 채우고 정규화로 중복 제거 → 재사용성↑. DBMS와 무관. 모델링의 최종 완료 상태.

3단계 · 물리적

물리적 모델링

실제 DBMS 구축. CREATE TABLE·인덱스·파티션·자료형 명시. 성능·보안·가용성 고려.

🏠 집 짓기로 비유

개념적 = '방3·거실1' 손스케치 → 논리적 = 치수·배관까지 그린 설계도면 → 물리적 = 벽돌로 실제 시공. 뒤로 갈수록 구체적·기술적이 됩니다.

단계결과물비유
1. 개념적 모델링핵심 엔터티·관계 ERD (큰 그림)손으로 그린 스케치
2. 논리적 모델링속성·키 상세 ERD + 정규화정식 건축 도면
3. 물리적 모델링DBMS별 CREATE TABLE + 인덱스·파티션시공 계획서
→ 운영데이터가 쌓인 실제 데이터베이스입주 완료된 건물
!

시험 포인트  3단계 순서 개념 → 논리 → 물리와 각 산출물. 정규화는 '논리' 단계에서 수행합니다.

데이터 모델링의 3가지 관점

관점내용분석 활동
데이터 관점업무가 관리하는 데이터(엔터티·속성) — 무엇을(What)구조 분석(정적 분석)
프로세스 관점업무가 실제 하는 일 — 어떻게(How)시나리오 분석(동적 분석)
데이터+프로세스 상관 관점프로세스가 데이터에 미치는 영향 — 언제(When)CRUD 매트릭스
!

시험 포인트  "CRUD 매트릭스"가 보이면 데이터와 프로세스의 상관 관점입니다. 관점은 데이터·프로세스·상관 세 가지뿐 — "기술 관점(Technical)"은 없는 보기(함정)!

좋은 데이터 모델의 요소 (6가지)

요소의미
① 완전성업무에 필요한 데이터를 빠짐없이 담았는가
② 중복 배제같은 데이터가 여러 곳에 흩어져 있지 않은가
③ 업무 규칙회사의 규칙이 모델에 녹아 있는가
④ 데이터 재사용다른 업무에서도 활용할 수 있는가
⑤ 의사소통보는 사람마다 같은 의미로 읽히는가
⑥ 통합성같은 데이터는 한 곳에만 정의되어 있는가

데이터 모델링 유의점 (3가지) 빈출

중복
Duplication

같은 데이터가 여러 테이블에 중복 저장되지 않도록.

비유연성
Inflexibility

업무 변화에 유연하게 대응하도록 설계. 데이터 정의와 프로세스를 분리.

비일관성
Inconsistency

데이터 간 상호 연관 관계를 명확히 정의해 모순이 없도록.

!

시험 포인트  모델링 유의점 = 중복·비유연성·비일관성 세 가지. "성능을 위해 초기부터 반정규화를 적극 수행"은 유의점이 아님(함정).

2. ERD 작성 절차 시험 단골

ERD는 엔터티와 관계를 그리는 표준 방법(1976년 피터 첸 고안). 작성은 6단계 순서로 진행되며 이 순서가 자주 출제됩니다.

1

엔터티를 도출하고 그린다

업무에서 관리할 집합(덩어리)을 찾습니다.

2

엔터티를 배치한다

중요한 엔터티를 왼쪽 상단에 배치합니다.

3

엔터티 간 관계를 설정한다

연결되는 엔터티끼리 선을 긋습니다.

4

관계명을 서술한다

어떤 행위/존재가 있는지 이름을 붙입니다.

5

관계 참여도를 표현한다

서로 몇 개씩 참여하는지(예: 고객1 : 계좌N).

6

관계의 필수 여부를 표현한다

반드시 있어야 하는 관계인지 표시합니다.

★

암기팁  "누가 있나(1·2) → 어떻게 잇나(3) → 이름(4) → 몇 개(5) → 필수(6)". 관계 3종(관계명→참여도→필수)은 항상 뒤쪽에 옵니다.

❓ 확인 퀴즈 · ERD 절차
ERD 작성 절차로 올바른 것은? (ㄱ엔터티도출 · ㄴ배치 · ㄷ관계설정 · ㄹ관계명 · ㅁ참여도 · ㅂ필수여부)
정답 ① 도출→배치→관계설정→관계명→참여도→필수여부. 관계명·참여도·필수여부 순서를 헷갈리지 마세요.

3. 3층 스키마 (ANSI/SPARC)

사용자·설계자·개발자가 DB를 보는 관점을 3단계로 나눈 ANSI 표준. 목적은 데이터 독립성 확보입니다.

🎬 쉽게 말하면

영화관에서 관객은 스크린만(외부), 기획자는 전체 구성을(개념), 영사기사는 필름 작동을(내부) 봅니다. 관점을 나눠두면 한쪽이 바뀌어도 다른 쪽이 안 흔들립니다.

스키마관점 / 개수내용
외부 스키마사용자·응용 / 여러 개사용자 뷰(View). 업무상 관련 데이터만 접근. 사용자·개발자가 다룸.
개념 스키마설계자(DA) / 1개조직 전체가 공유하는 통합 ERD. 모든 규칙·구조의 원본.
내부 스키마개발자(DBA) / 1개물리적 저장구조. 데이터 파일·레코드·필드·인덱스·파티션.
!

시험 포인트  "물리적 저장구조·레코드·필드·인덱스" → 내부 스키마. "사용자 뷰" → 외부. "전체 통합 설계" → 개념. 외부만 여러 개, 개념·내부는 각 1개.

데이터 독립성 2가지

종류의미
논리적 독립성개념 스키마가 변경돼도 외부 스키마(응용)는 영향 없음 (개념 ↔ 외부)
물리적 독립성내부 스키마가 변경돼도 개념·외부 스키마는 영향 없음 (내부 ↔ 개념)
!

함정  인덱스·파티션 변경은 저장 구조(내부 스키마)의 일이므로 물리적 독립성입니다. 논리적 독립성으로 착각하지 마세요.

4. 엔터티 (Entity)

업무에서 관리해야 하는 정보의 덩어리(명사). 실제 테이블의 후보가 됩니다.

📦 쉽게 말하면

엔터티는 엑셀 시트 한 장의 제목('회원' 시트, '주문' 시트)이에요. 그 안의 한 줄 한 줄이 인스턴스(행), 열 제목이 속성입니다. 표 자체가 엔터티, 헤더가 속성, 각 행이 인스턴스.

엔터티의 5가지 특징 — '업·식·인·속·관'

업 — 업무에 필요
관리할 가치가 있는 정보여야 한다.
식 — 식별 가능
식별자로 유일하게 구분된다.
인 — 인스턴스 ≥ 2
2개 이상의 행이 존재해야 한다.
속 — 속성 ≥ 2
2개 이상의 속성을 가진다.
관 — 관계 보유
다른 엔터티와 최소 1개 이상의 관계를 가진다.
!

함정  개수 조건이 포인트 — 인스턴스·속성은 각각 2개 이상이어야 합니다. "속성이 1개뿐인 엔터티도 있다"는 틀린 보기.

엔터티의 종류 — 2가지 분류 기준

① 유형·무형 (형태 유무)
유형 엔터티
물리적 형태 있음 (사원, 상품, 매장)
개념 엔터티
형태 없이 개념적 (부서, 조직, 보험상품)
사건 엔터티
행위로 발생 (주문, 결제, 청구)
② 발생 시점
기본(키) 엔터티
스스로 생성 (사원, 부서, 고객)
중심 엔터티
기본에서 발생, 업무 중심 (주문, 계약, 매출)
행위 엔터티
2개 이상 부모에서 발생 (주문상세, 이력)
!

헷갈림 주의  사건 엔터티는 '유형/무형' 쪽입니다. '발생 시점'은 기본·중심·행위. 또 "주문"은 업무에 늘 있어도 고객·상품에서 발생하므로 중심 엔터티(기본 아님).

엔터티 명명 규칙

  • 현업에서 사용하는 업무 용어를 사용한다.
  • 약어 사용을 지양한다.
  • 단수 명사를 사용한다.
  • 모델 전체에서 유일한 이름이어야 한다.

5. 속성 (Attribute)

엔터티가 가지는 세부 정보 항목(컬럼). 더 이상 분해되지 않는 최소 단위입니다.

  • 업무에서 관리되는 정보이다.
  • 하나의 값(원자값)만 가진다.
  • 주식별자에 함수적으로 종속된다 (기본키가 정해지면 값이 결정됨).

속성의 3가지 분류 기준

기준종류설명 (예)
① 특성
(어디서 왔나)		기본 속성업무에서 직접 추출 (이름, 전화번호, 주소)
설계 속성설계 과정에서 새로 만든 것 (회원ID, 상품코드)
파생 속성다른 속성에서 계산 (총주문금액 = 수량 × 단가)
② 분해 여부단순(원자) 속성더 못 쪼갬 (이름, 나이)
복합 속성여러 의미 결합 (주소 = 시+구+동)
③ 값 개수단일값 속성하나만 가짐 (주민번호)
다중값 속성여러 개 가능 → 별도 엔터티로 분리 (전화번호: 집·휴대폰)
!

시험 포인트  ① "주민번호로부터 구한 나이" = 파생 속성. ② 파생 속성은 정합성 부담이 커 최소화가 원칙("많을수록 좋다"는 틀림). ③ 한 속성엔 값 하나만(원자값) — 다중값은 1정규형 위반.

구성에 따른 분류

속성은 역할에 따라 PK 속성(기본키), FK 속성(외래키), 일반 속성으로도 나뉩니다.

속성 명명 규칙

  • 코드가 아닌 현업 용어로 명명한다.
  • 명사형으로 ('주문수량' O, '주문은얼마인가' 서술식 X).
  • 약어 사용을 자제한다 ('qty'보다 '수량').
  • 전체 모델에서 유일한 이름을 쓴다.
도메인(Domain)

속성이 가질 수 있는 값의 범위 — 타입 + 크기 + 제약(허용값)을 모두 포함. 예: '성별'의 도메인은 CHAR(1) / {'M','F'}만 허용. NULL 허용 여부도 도메인의 일부.

★

헷갈림 주의  복합 속성(한 속성을 여러 의미로 쪼갬, 주소=시+구+동)과 복합 식별자(여러 속성을 묶어 PK로 씀)는 다른 개념입니다.

6. 관계 (Relationship)

두 엔터티가 서로 어떻게 연결되어 있는지 표현한 것. 존재 관계(상태로 엮임, 예: 부서에 사원 소속)와 행위 관계(행동으로 엮임, 예: 회원이 주문 발주)로 나뉩니다. 양방향 동사로 표현해요(주문하다/주문되다).

관계의 4요소

요소설명예
관계명 (Membership)두 엔터티를 잇는 동사·역할명주문하다 / 주문되다
관계차수 (Cardinality)몇 대 몇인가1:1, 1:N, M:N
관계선택성 (Optionality)필수인가 선택인가필수 / 선택
관계방향 (Direction)양방향 모두 명명회원→주문 / 주문→회원

관계 차수(Cardinality)

차수의미예
1 : 1완전 1:1(반드시) / 선택적 1:1(없을 수도)사원 ↔ 사원증
1 : N한쪽이 하나일 때 상대는 여럿부서 1 → 사원 N, 회원 1 → 주문 N
M : N양쪽 모두 여럿 → 그대로 구현 불가학생 ↔ 과목
!

시험 포인트  M:N 관계는 그대로 두면 다중값/카티션 곱 문제가 생겨, 중간에 교차(연결) 엔터티를 넣어 1:N + N:1로 해소합니다.

관계 선택성(Optionality)

종류표기의미
필수 (Mandatory)| (막대)반드시 있어야 함 (주문엔 반드시 회원이 있어야)
선택 (Optional)○ (고리)있을 수도 없을 수도 (회원이 쿠폰은 없을 수도)

식별 관계 vs 비식별 관계

식별 관계 (실선)

부모의 기본키를 자식의 기본키 일부로 포함(강한 종속). 부모 없이 자식 존재 불가. (예: 주문 ↔ 주문상세)

비식별 관계 (점선)

부모의 기본키를 자식의 일반 속성(FK)으로만 참조(약한 종속). 부모 없어도 자식 존재. (예: 부서 ↔ 사원)

!

함정  ERD는 존재 관계와 행위 관계를 구분하지 않고 하나의 표기로 그립니다. 실선·점선으로 연관·의존을 구분하는 것은 UML입니다.

ERD 표기법 — 바커 vs IE

관계의 차수(얼마나)와 선택성(필수인지)을 그림 기호로 나타냅니다. 두 표기법이 자주 비교됩니다.

IE 표기법 (정보공학 · 까마귀발)

다수(N)를 까마귀발(crow's foot)로 표현. 필수= |, 선택= ○. 실선·점선으로 식별·비식별을 구분. 가장 널리 쓰입니다.

바커(Barker) 표기법

관계선의 실선=필수, 점선=선택으로 선택성(참여)을 표현. 다수는 까마귀발. Oracle 계열에서 사용.

★

암기팁  공통으로 까마귀발 = 다수(N). 단, 실선·점선의 뜻이 달라요 — IE는 식별/비식별, Barker는 필수/선택. "○가 붙으면 0개 가능(선택)".

7. 엔터티 식별자 (Identifier)

엔터티 안의 인스턴스를 서로 구분해 주는 유일한 표식. 테이블의 기본키(Primary Key)가 됩니다.

주식별자(기본키)의 4가지 조건 — '유·최·불·존'

1

유일성

모든 인스턴스를 유일하게 구분.

2

최소성

꼭 필요한 속성만으로 구성 (정규화와 직결).

3

불변성

한 번 정해지면 거의 변하지 않음.

4

존재성

NULL이 될 수 없음 (NOT NULL).

★

참고  주식별자 조건은 유일성·최소성·불변성·존재성입니다. '대표성'은 아래 식별자 분류 기준(대표성)에 등장하는 개념으로, 교재에 따라 주식별자 특성에 함께 넣기도 합니다.

데이터 모델과 SQL

정규화·반정규화·관계와 조인·트랜잭션·NULL·식별자를 다룹니다. 특히 정규화 단계 구분과 관계=FK=JOIN의 흐름은 거의 매번 나오는 핵심입니다.

1. 정규화 (Normalization)

데이터의 중복을 없애고 이상현상을 막기 위해 테이블을 작은 단위로 분리하는 과정입니다.

💡 쉽게 말하면

정규화는 '중복 정리정돈'이에요. 한 표에 같은 정보가 여기저기 중복되면 수정할 때 다 바꿔야 하고 실수가 생기죠. 그래서 겹치는 걸 떼어내 표를 쪼갭니다. 대신 표가 늘어나 조회 때 조인(JOIN)이 많아질 수 있어요.

정규화하면 입력·수정·삭제 성능은 일반적으로 향상, 조회 성능은 조건에 따라 향상되거나 저하(조인 증가 때문). 중복 제거 → 무결성↑, 저장공간↓.

이상현상 (Anomaly) 3가지 — 정규화가 막으려는 것

삽입 이상

데이터를 넣으려는데 다른 정보가 없어 못 넣음. (학생 등록하려는데 수강과목 칸을 비울 수 없음)

갱신 이상

한 곳만 바꿨는데 다른 곳이 안 바뀜. (회원 주소 1곳만 수정 → 데이터 불일치)

삭제 이상

데이터를 지우려다 필요한 정보까지 사라짐. (마지막 수강 취소했는데 학생 정보까지 삭제)

정규화 단계 — 이것만 외우면 됩니다

단계핵심 규칙키워드
제1정규화 (1NF)모든 속성은 하나의 값(원자값)만 (다중값·반복그룹 제거)원자값 / 반복그룹
제2정규화 (2NF)일반 속성은 주식별자 전체에 종속 (부분종속 제거)부분함수 종속 제거
제3정규화 (3NF)일반 속성끼리 종속 금지 (키 외 칼럼 간 종속 제거)이행함수 종속 제거
BCNF모든 결정자가 후보키여야 함 (더 엄격한 3NF)결정자 = 후보키
★

암기팁  1NF=여러 값/반복, 2NF=부분 종속(복합키일 때 일부에만 종속), 3NF=이행 종속(A→B→C라 A→C 성립). "부분" 보이면 2, "이행" 보이면 3!

🔎 부분종속 vs 이행종속

부분종속(2정규화): PK가 (학생ID, 과목ID)인데 '학생이름'이 학생ID에만 딸림 → 주식별자 일부에만 종속. 이행종속(3정규화): 사원ID → 부서ID → 부서명 처럼 키가 아닌 것(부서ID)을 통해 부서명이 결정 → 일반 속성끼리 종속.

BCNF (보이스-코드 정규형)

제3정규형을 더 강화한 단계입니다. 모든 결정자(다른 속성을 결정하는 속성)가 후보키여야 한다는 규칙으로, 후보키가 아닌 결정자를 분리합니다.

💡 쉽게 말하면

정규화 순서는 1 → 2 → 3 → BCNF → 4 → 5. 예: PK가 (학생, 과목)인데 "한 강사는 한 과목만 가르친다(강사→과목)"면, 후보키가 아닌 '강사'가 '과목'을 결정 → BCNF 위반. 시험에선 "3정규형보다 강한 정규형 = BCNF, 모든 결정자가 후보키" 정도면 됩니다.

정규화의 장단점

장점단점
데이터 중복 제거테이블이 많아짐
이상현상 방지 · 무결성↑조인이 늘어남
입력·수정·삭제 성능·유지보수 용이조회 성능 일부 저하 가능
❓ 확인 퀴즈 · 정규화
정규화에 대한 설명이 아닌 것은?
정답 ④ 정규화로 테이블이 늘면 조인이 늘어 조회 성능이 저하될 수도 있습니다. '반드시 향상'은 틀림.

2. 반정규화 (De-Normalization)

조회 성능을 위해 중복을 허용하거나 그룹핑하는 과정. 정규화가 끝난 뒤 성능 이슈가 있을 때만 고려합니다.

조회 성능 ↑, 그러나 입력·수정·삭제 성능 ↓ + 정합성(무결성) 저해 위험. 단순히 같은 데이터를 여러 테이블에 두는 건 정합성 위배가 될 수 있어 신중해야 합니다.

구분기법
테이블 반정규화테이블 병합(1:1, 1:M) / 분할(수직·수평) / 추가(중복·통계·이력·부분)
컬럼 반정규화중복 컬럼 추가 / 파생 컬럼 추가 / 이력 테이블 컬럼 추가
관계 반정규화중복 관계 추가
수직 분할

일부 속성(컬럼)을 별도 테이블로 → 1:1 관계 2개 생성. (자주 쓰는 컬럼 / NULL 많은 컬럼 분리)

수평 분할

일부 인스턴스(행)를 특정 기준(주로 기간)으로 분할 = 파티셔닝.

!

시험 포인트  수직=컬럼 분할(1:1), 수평=행 분할(파티셔닝). '백업 테이블 추가'는 반정규화 기법이 아님(함정).

슈퍼타입 / 서브타입 변환 (기출)

타입방식특징

Single전부 하나의 테이블로 통합조인 성능 best, 관리 편리 (입출력은 나쁨)
❓ 확인 퀴즈 · 반정규화
반정규화의 기법이 아닌 것은?
정답 ② 테이블 추가 기법 = 중복·통계·이력·부분. '백업'은 포함되지 않습니다.

3. 관계와 조인의 이해 관계=FK=JOIN

모델에서의 관계는 외래키(FK)로 구현되고, 그 관계를 따라 여러 테이블을 합쳐 보는 작업이 조인(JOIN)입니다.

💡 쉽게 말하면

영수증엔 주문 정보만, 회원카드엔 회원 정보만 있어요. 같은 사람의 영수증과 카드를 맞춰 보면 "김철수가 사과 2개 샀구나"가 보이죠 — 흩어진 정보를 키로 맞춰 합치는 것이 조인입니다.

1

관계 (설계·개념 모델)

두 엔터티의 의미적 연결("회원이 주문을 한다")을 ERD 선으로 표현.

2

외래키 FK (논리·물리 모델)

자식 테이블이 부모 테이블의 PK를 참조하는 컬럼. FK = 조인 키.

3

조인 JOIN (SQL 실행)

FK = PK 조건으로 두 테이블을 합쳐 한 결과로 조회.

조인의 4가지 종류 (개념 미리보기)

종류의미비유

4. 트랜잭션 (Transaction)

함께 성공하거나 함께 실패해야 하는 하나의 논리적 작업 단위. "죽어도 한 세트로 묶이는" 작업입니다.

💡 쉽게 말하면

계좌 이체 = '출금(A −1만)' + '입금(B +1만)'이 한 묶음. 입금이 실패하면 출금도 롤백(취소)돼야 하죠. 전부 성공 아니면 전부 취소 — 이게 트랜잭션입니다.

트랜잭션 4대 특징 — ACID (원·일·고·지)

원자성 (Atomicity)

전부 반영되거나 전부 취소. 중간은 없다.

일관성 (Consistency)

실행 전후 무결성 규칙이 유지된다.

고립성 (Isolation)

동시 실행이라도 서로 간섭하지 못함.

지속성 (Durability)

커밋된 결과는 시스템이 죽어도 영구 보존.

Partially Committed마지막 SQL까지 무사 통과
CommittedCOMMIT으로 영구 반영
Failed → Aborted오류 발생 → ROLLBACK으로 취소 종료

관계의 식별성 (식별 관계·실선)주문상세는 주문 PK를 자기 PK로 가짐 → 주문 없이 존재 불가. DELETE 시 함께 처리 또는 차단
선택 관계 (Optional)고객은 주문이 없을 수 있음 → 각각 별도 트랜잭션으로 처리 가능

!

시험 포인트  ① 미커밋 데이터를 읽었다 → 고립성 위반. 커밋 후 유실 → 지속성 위반. ② 원자성(전부/전무)과 일관성(무결성 유지)은 다른 개념. ③ 양쪽 필수 관계 = 한 트랜잭션, 선택 관계 = 별도 트랜잭션 가능.

5. NULL 속성의 이해

값이 존재하지 않음(또는 아직 모름). 0이나 공백('')과는 전혀 다릅니다.

구분숫자 0공백 ' 'NULL
데이터 존재있음있음 (문자 한 칸)없음
비교 가능가능가능불가 (= NULL 안 됨)
산술 연산가능—불가 (결과 NULL)

NULL 연산 규칙

상황NULL 처리
가로 연산 (수입 − 지출 등 컬럼끼리)하나라도 NULL이면 결과는 NULL
세로 연산 (SUM·AVG 등 집계)NULL을 제외하고 계산
NULL 비교 (COL = NULL 등)결과는 늘 UNKNOWN(참 아님) → 행 제외
🔎 SQL 3-값 논리

일반 프로그래밍은 TRUE/FALSE 2값이지만, SQL은 NULL 때문에 TRUE / FALSE / UNKNOWN 3값입니다. NULL = NULL도 결과가 UNKNOWN. WHERE 절은 TRUE인 행만 남기므로 = NULL은 항상 0건 → 반드시 IS NULL / IS NOT NULL을 써야 합니다.

NULL 처리 함수

함수동작
NVL(A, B)A가 NULL이면 B, 아니면 A
NVL2(A, B, C)A가 NULL이 아니면 B, NULL이면 C
NULLIF(A, B)A = B이면 NULL, 다르면 A
COALESCE(A, B, C …)NULL이 아닌 최초의 값 반환
!

시험 포인트  ①NULL ≠ 0, NULL ≠ ''  ②NULL과의 사칙연산 = NULL  ③집계함수(SUM/AVG/COUNT(컬럼))는 NULL 제외, COUNT(*)만 NULL 포함  ④AVG는 NULL을 0이 아니라 분모·분자 모두에서 제외(0으로 보려면 AVG(NVL(컬럼,0))).

6. 본질 식별자 vs 인조 식별자

본질 식별자

업무에서 자연스럽게 도출. 의미 있음 (주민번호, 사업자번호, ISBN, 학번). = 원조 식별자.

인조 식별자

인위적으로 부여. 의미 없음 (자동증가 ID, UUID). 복합식별자가 복잡할 때 대체 = 대리 식별자.

장단점 비교

항목본질 식별자인조 식별자
의미업무적 의미 있음의미 없음 (단순 키)
변경 위험있음 (업무 규칙 변동 시)없음 (부여 후 영구 고정)
길이길 수 있음짧고 일관
데이터 품질 검증가능 (중복 자연 검출)어려움 (별도 UNIQUE 필요)
장점직관적·데이터 검증 용이JOIN·인덱스 효율, 보안(개인정보 노출 회피)
★

현업 권장 패턴  PK는 인조 식별자(짧은 ID)로 두고, 본질키는 UNIQUE 제약으로 별도 보존 → 보안·성능·일관성을 모두 만족. 인조 식별자만 쓰면 같은 업무 데이터가 다른 번호로 중복 입력될 수 있어 UNIQUE가 필수입니다.

!

시험 포인트  "업무 행위 없이도 부여될 수 있다" → 인조 식별자. 본질 식별자는 업무 수행 과정에서 값이 정해집니다. 인조 식별자를 쓰는 경우 = 본질키가 복합키로 너무 길거나, 자주 바뀌거나, 의미 노출이 곤란할 때.

★

핵심  ① 결과의 헤더(컬럼명)는 첫 번째 쿼리를 따라감. ② ORDER BY는 맨 마지막에 한 번만. ③ MINUS=Oracle, EXCEPT=SQL Server(같은 차집합).

4. 그룹 함수 (ROLLUP · CUBE · GROUPING SETS)

소계(소그룹별 합)와 총계를 구하는 함수들입니다. 이게 SQL 활용에서 제일 어렵지만, "무엇으로 그룹핑되는가"만 비교하면 됩니다.

함수그룹핑 결과 (A, B 기준)
ROLLUP(A,B)①A,B별 ②A별 ③총계  (한 방향 소계)
CUBE(A,B)①A,B별 ②A별 ③B별 ④총계  (모든 조합)
GROUPING SETS(A,B)①A별 ②B별  (지정한 것만, 총계 없음)
💡 핵심 직관

ROLLUP = 계단식 소계(왼→오 한 방향). CUBE = 가능한 모든 조합의 소계(다차원). GROUPING SETS = 내가 지정한 묶음만 개별 집계. 총계가 필요하면 인자에 ()를 추가하거나 ROLLUP을 쓰면 됩니다.

!

시험 포인트  괄호 묶음은 "한 덩어리"로 취급. ROLLUP((A,B), C) → (A,B),C별 → (A,B)별 → 총계. "결합 가능한 모든 집계" = CUBE.

❓ 확인 퀴즈 · 집합 연산자
차집합과 같은 역할을 하는 집합 연산자는?
정답 ② 차집합 = MINUS(Oracle) / EXCEPT(SQL Server). 교집합은 INTERSECT.
2과목 · PART 3-3

관리 구문

SQL 명령어를 4종류로 나눠 익힙니다. DML·TCL·DDL·DCL — 어느 명령어가 어디 속하는지가 단골 출제 포인트입니다.

분류풀이명령어
DML데이터 조작어INSERT, UPDATE, DELETE, (SELECT), MERGE
TCL트랜잭션 제어어COMMIT, ROLLBACK, SAVEPOINT
DDL데이터 정의어CREATE, ALTER, DROP, RENAME, TRUNCATE
DCL데이터 제어어GRANT, REVOKE (+ CREATE/ALTER/DROP USER)
★

암기팁  헷갈리는 두 가지: COMMIT/ROLLBACK은 TCL(DDL 아님!), TRUNCATE는 DDL(DML 아님!). GRANT/REVOKE는 DCL.

1. DML — 데이터 조작어

명령어설명주의
INSERT데이터 입력PK·NOT NULL 컬럼엔 NULL 입력 불가
UPDATE데이터 수정WHERE 없으면 전체 행 수정
DELETE데이터 삭제WHERE 없으면 전체 행 삭제. COMMIT 전 ROLLBACK 가능
MERGE입력+수정을 한 번에 (ON 조건으로 MATCHED/NOT MATCHED 분기)동기화·백업에 유용
🔎 DELETE vs TRUNCATE vs DROP

DELETE: 행만 삭제, ROLLBACK 가능, 로그 남김. TRUNCATE: 전체 행 삭제 + 저장공간 초기화, ROLLBACK 불가(DDL), 빠름, 구조는 유지. DROP: 테이블 구조까지 통째 삭제. "연인과 깔끔히 헤어지는 TRUNCATE, 미련 남기는 DELETE"로 기억!

!

시험 포인트  1억 건을 로그 없이 빠르게 비우고 테이블은 유지 → TRUNCATE. DML은 COMMIT해야 디스크 반영(단 SQL Server는 DML도 AUTO COMMIT).

2. TCL — 트랜잭션 제어어

명령어설명
COMMIT변경 내용 확정·반영. 해야 최종 저장
ROLLBACK변경 내용 취소, 이전 값 복구
SAVEPOINT중간 지점 저장 → ROLLBACK TO 지점으로 일부만 되돌림
★

핵심  COMMIT 전까지는 메모리에만 있어 다른 사용자는 못 봄. 오래 COMMIT/ROLLBACK 안 하면 LOCK이 걸려 남이 수정 못 함.

3. DDL — 데이터 정의어

데이터 유형 — CHAR vs VARCHAR

CHAR (고정 길이)

정한 크기를 항상 다 차지. 'IU'를 CHAR(10)에 넣으면 10byte. 비교 시 공백 무시 → 'IU'='IU  '.

VARCHAR (가변 길이)

실제 크기만 사용. 'IU'는 2byte. 비교 시 공백도 문자 → 'IU'≠'IU  '.

※ 영어 1글자=1byte, 한글 1글자=3byte(캐릭터셋에 따라 2byte)로 크기를 계산.

주요 명령어

명령어설명
CREATE TABLE테이블 생성 (컬럼·데이터유형·크기·제약조건 정의)
ALTER ... ADD컬럼/제약조건 추가 (컬럼은 항상 맨 끝에)
ALTER ... MODIFY데이터유형·DEFAULT·NOT NULL 변경
ALTER ... DROP COLUMN컬럼 삭제 (복구 불가)
ALTER ... RENAME COLUMN컬럼명 변경
DROP TABLE테이블 삭제. 참조 테이블 있으면 CASCADE CONSTRAINT 필요
TRUNCATE TABLE전체 행 삭제 + 공간 초기화 (ROLLBACK 불가)
🔎 CTAS & 제약조건

CTAS(CREATE TABLE ~ AS SELECT ~): 기존 테이블 복사 생성. 단 NOT NULL만 복사되고 PK·UNIQUE·CHECK는 초기화 → 필요 시 ALTER로 재정의. 제약조건: PRIMARY KEY, UNIQUE, NOT NULL, CHECK(값 범위 지정), FOREIGN KEY(참조 무결성).

!

시험 포인트  컬럼 데이터유형/DEFAULT/NOT NULL 변경 → MODIFY. 컬럼 추가 → ADD. CASCADE는 Oracle만 있고 SQL Server엔 없음.

4. DCL — 데이터 제어어

💡 쉽게 말하면

DB를 '집'이라 하면 USER는 '룸메이트'. 먼저 사람을 들이고(CREATE USER + 비밀번호), 집을 쓸 권한을 줘야(GRANT) 방에 들어갈 수 있어요. 권한 회수는 REVOKE.

명령어설명
GRANT 권한 TO 사용자권한 부여 (예: GRANT CREATE TABLE TO PERPEAR)
REVOKE 권한 FROM 사용자권한 회수
ROLE여러 권한을 하나로 묶은 세트 (빅맥세트처럼). ROLE을 사용자에게 GRANT
❓ 확인 퀴즈 · 명령어 분류
다음 중 DDL이 아닌 것은?
정답 ② COMMIT은 TCL. DDL은 CREATE·ALTER·DROP·RENAME·TRUNCATE입니다.
2과목 · 빈출 보충

꼭 나오는 SQL 보충

교안에는 간략했지만 기출에 반드시 나오는 조인·계층형 쿼리·윈도우 함수·연산자 우선순위·CASE를 한 번에 정리했습니다. 2과목 고득점의 열쇠입니다.

1. JOIN (조인)

두 테이블을 연결해 조회합니다. 결과 건수를 묻는 문제가 자주 나옵니다.

종류설명
INNER JOIN양쪽에 모두 있는 행만 (교집합)
LEFT OUTER왼쪽 전부 + 매칭되는 오른쪽 (없으면 NULL)
RIGHT OUTER오른쪽 전부 + 매칭되는 왼쪽
FULL OUTER양쪽 전부 (매칭+비매칭 모두)
CROSS JOIN두 테이블 행의 곱 (카테시안 곱)
!

시험 포인트  ① INNER JOIN에서 ON이 빠지면 CROSS JOIN과 같은 결과(행의 곱). ② Oracle의 (+)는 ANSI OUTER JOIN으로 변환되는데, (+)가 왼쪽에 있으면 RIGHT OUTER, 오른쪽에 있으면 LEFT OUTER. ③ USING·NATURAL JOIN의 공통 컬럼엔 테이블명/별칭을 붙이지 않음.

🔎 건수 계산 예

A테이블 4행, B테이블 3행, 공통 2건이면 → INNER 2, LEFT 4, RIGHT 3(공통2+B단독1 형태에 따라), FULL 5, CROSS 4×3=12. 벤다이어그램으로 "어느 쪽을 다 살리나"를 떠올리세요.

2. 계층형 쿼리 (Hierarchical Query)

조직도·게시판 댓글처럼 부모-자식 구조를 조회합니다 (SELF JOIN 형태).

SELECT LEVEL, 사원 FROM 사원테이블 START WITH 상위사원 IS NULL -- 루트(시작점) CONNECT BY PRIOR 사원 = 상위사원; -- 부모→자식 전개
구문의미
LEVEL현재 깊이(Depth). 루트=1. 리프가 가장 큰 값
START WITH시작(루트) 노드 지정
CONNECT BY부모-자식 연결 규칙. PRIOR 위치로 순/역방향 결정
SYS_CONNECT_BY_PATH루트부터 현재까지 경로 출력
CONNECT_BY_ROOT최상위 루트 값 표시
CONNECT_BY_ISLEAF최하위(리프)면 1, 아니면 0
NOCYCLE순환(CYCLE) 발생 시 멈춤
!

시험 포인트  ① PRIOR 위치에 따라 순방향/역방향 전개 가능. ② WHERE는 START WITH…CONNECT BY로 전개가 끝난 뒤 필터링. ③ TRIM은 계층형 함수가 아님(함정). ④ 동일 레벨 정렬은 ORDER SIBLINGS BY.

3. 윈도우 함수 (Window Function)

행을 그룹으로 묶지 않고도 그룹별 계산·순위를 각 행 옆에 보여줍니다. OVER()가 핵심.

SELECT 사원, 급여, RANK() OVER(PARTITION BY 부서 ORDER BY 급여 DESC) 순위 FROM 사원; -- 부서별로 급여 높은 순 순위

순위 함수 (★빈출)

함수동점 처리 (1,1 다음)
RANK동점은 같은 순위, 다음은 건너뜀 (1,1,3)
DENSE_RANK동점은 같은 순위, 다음은 안 건너뜀 (1,1,2)
ROW_NUMBER동점도 무조건 순차 (1,2,3)

기타 함수 & 윈도우 범위

구문의미
FIRST_VALUE / LAST_VALUE정렬 후 첫 / 마지막 값
LAG / LEAD이전 / 다음 행 값
RATIO_TO_REPORT파티션 합계 중 비율
CUME_DIST / PERCENT_RANK누적 백분율 (0~1)
NTILE(n)n개 등급으로 분할
ROWS / RANGE행 자체 기준 / 값 기준
UNBOUNDED PRECEDING시작점에만 사용(파티션 첫 행)
UNBOUNDED FOLLOWING끝점에만 사용(파티션 마지막 행)
!

시험 포인트  RANK vs DENSE_RANK 차이(건너뛰기 유무)가 단골. UNBOUNDED PRECEDING은 끝점에 못 옴. 비율 함수(CUME_DIST·PERCENT_RANK·RATIO_TO_REPORT)는 0~1 범위.

4. 연산자 우선순위 · SQL 실행 순서

연산자 우선순위

산술 → 연결(||) → 비교 → IN·LIKE·BETWEEN·IS NULL → NOT → AND → OR

SQL 실행 순서

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY

★

암기팁  실행 순서: "프 → 웨 → 그 → 하 → 셀 → 오". SELECT는 거의 마지막, ORDER BY가 진짜 마지막. 작성 순서와 실행 순서가 다른 점이 함정!

5. CASE · DECODE · 기타 자주 나오는 것

구문설명
CASE WHEN 조건 THEN … ELSE … ENDIF-THEN-ELSE 논리. 범위 조건 가능
DECODE(컬럼, A, 결과1, 기본값)Oracle 전용. = 비교만 가능
NULL 비교반드시 IS NULL / IS NOT NULL (CASE로 =NULL 비교 불가!)
ANY / ALLANY=하나라도 만족, ALL=모두 만족 (다중행)
COUNT(*) vs COUNT(컬럼)*는 NULL 포함 전체, 컬럼은 NULL 제외
순수 관계 연산자SELECT, PROJECT, JOIN, DIVIDE
!

시험 포인트  ① CASE COL WHEN NULL THEN…은 NULL을 못 잡음 → 반드시 IS NULL. ② DISTINCT COL1, COL2 = GROUP BY COL1, COL2(중복 제거). ③ 정규표현식 ^=시작, $=끝.

❓ 확인 퀴즈 · 실행 순서
SQL문의 실행 순서로 올바른 것은?
정답 ① FROM으로 테이블 선택 → WHERE 필터 → GROUP BY/HAVING 그룹 → SELECT 인출 → ORDER BY 정렬.

6. GROUP BY · HAVING

데이터를 묶어서 집계(합계·평균·개수 등)할 때 씁니다.

SELECT 부서, COUNT(*) FROM 사원 WHERE 급여 > 3000 -- ① 그룹 전 행 필터 GROUP BY 부서 -- ② 부서별로 묶기 HAVING COUNT(*) >= 5; -- ③ 그룹 후 조건
!

시험 포인트  ① WHERE는 그룹 전, HAVING은 그룹 후 필터. ② SELECT에 집계함수와 함께 쓴 일반 컬럼은 반드시 GROUP BY에 들어가야 함. ③ 집계함수(SUM/AVG/COUNT(컬럼))는 NULL 제외, COUNT(*)만 NULL 포함.

7. 조인 보충 — SELF · NATURAL · ANSI

조인설명
SELF JOIN한 테이블을 자기 자신과 조인 (별칭 2개 사용). 사원-상사 관계 등
NATURAL JOIN두 테이블의 같은 이름·타입 컬럼을 자동으로 EQUI JOIN. 공통 컬럼에 테이블명·별칭 붙이면 안 됨
USING공통 컬럼 중 원하는 것만 골라 조인. 역시 별칭 금지
ON조인 조건을 직접 지정 (컬럼명 달라도 가능)
★

Oracle (+) ↔ ANSI 변환  (+)가 왼쪽에 있으면 → RIGHT OUTER JOIN, 오른쪽에 있으면 → LEFT OUTER JOIN. 기호 반대쪽을 다 살린다고 기억!

8. TOP-N 쿼리 (상위 N건 조회)

방식문법

9. PIVOT / UNPIVOT

PIVOT

행 → 열로 회전. 세로로 쌓인 데이터를 가로 표(교차표)로 집계. (예: 월별 매출을 '1월·2월·3월' 컬럼으로)

UNPIVOT

열 → 행으로 되돌림. 가로로 펼쳐진 컬럼을 세로 데이터로 변환.

💡 쉽게 말하면

엑셀 '피벗 테이블'과 같은 개념이에요. PIVOT = 세로 목록을 가로 요약표로, UNPIVOT = 그 반대. 방향만 기억하면 됩니다.

문제 06
반정규화를 적용하는 이유로 올바르지 않은 것은?
정답 ④ 반정규화는 중복을 허용(증가)해 성능을 올립니다. 중복을 감소시키는 건 정규화.
문제 08
카디널리티를 계산하는 식으로 올바른 것은?

정답 ③ 이행 함수 종속(키 외 칼럼 간 종속) 제거 = 제3정규화.

DROP TABLE 테이블명 [CASCADE CONSTRAINT]에 대한 설명으로 옳은 것은?
